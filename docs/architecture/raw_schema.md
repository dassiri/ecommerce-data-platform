# Raw / Landing Schema

Step: **3.3.2 — PostgreSQL Raw Schema & Ingestion Foundation**
Scope: database structure only. No CSV loading, no ingestion pipeline, no
checksum logic, no orchestration, no dbt/Airflow/Terraform.

## 1. Purpose of the Raw layer

`raw` is the Landing zone in the approved architecture:

```
CSV Sources → Python Ingestion → PostgreSQL Raw/Landing → Staging (dbt) → Curated (dbt) → Consumption (dbt Marts)
```

Its job is to hold an unmodified, structurally-typed copy of each source
CSV, plus operational ingestion metadata. It intentionally does **not**
enforce business correctness — that is the responsibility of later layers.
This mirrors the Step 1 finding "source data must not be silently cleaned
or deduplicated" and DEC-002.

## 2. The six Raw tables

| Raw table | Source file | Contract | Grain |
|---|---|---|---|
| `raw.users` | `users.csv` | `ingestion/contracts/users_contract.yml` | One row per `user_id` (source may contain duplicates; not deduplicated) |
| `raw.products` | `products.csv` | `ingestion/contracts/products_contract.yml` | One row per `product_id` |
| `raw.orders` | `orders.csv` | `ingestion/contracts/orders_contract.yml` | One row per `order_id` |
| `raw.order_items` | `order_items.csv` | `ingestion/contracts/order_items_contract.yml` | One row per `order_item_id` |
| `raw.reviews` | `reviews.csv` | `ingestion/contracts/reviews_contract.yml` | One row per `review_id` |
| `raw.events` | `events.csv` | `ingestion/contracts/events_contract.yml` | One row per `event_id` |

Each table's source columns are a direct, 1:1 mapping from its YAML data
contract — same names, same meaning. See
`docs/data_contracts/contract_reference.md` for the contract structure
itself.

### Source → PostgreSQL type mapping

| Contract `data_type` | PostgreSQL type | Notes |
|---|---|---|
| `string` | `TEXT` | No length constraint invented; contracts declare *patterns* (e.g. `^U[0-9]{6}$`) as deferred/DQ concerns, not schema constraints, so `TEXT` avoids inventing an arbitrary `VARCHAR(n)`. |
| `decimal` (financial: `price`, `total_amount`, `item_price`, `item_total`) | `NUMERIC(12,2)` | Per instruction: financial fields must use exact `NUMERIC`, never floating point. 12,2 comfortably covers the profiled ranges (source notes: up to ~7,950.74 / ~2,338.13) with headroom. |
| `decimal` (`products.rating`) | `NUMERIC(3,2)` | Bounded 0–5 per contract; `NUMERIC` chosen for consistency, even though this isn't currency. |
| `integer` (`order_items.quantity`, `reviews.rating`) | `INTEGER` | Matches contract type directly. |
| `date` (`users.signup_date`) | `DATE` | Matches contract format `YYYY-MM-DD`. |
| `timestamp` (`orders.order_date`, `reviews.review_date`, `events.event_timestamp`) | `TIMESTAMP` (no time zone) | Source values are ISO8601 strings with no explicit UTC offset (e.g. `2025-09-09T14:52:37.292731`). Stored as timezone-*naive* to faithfully mirror the source rather than assuming a timezone. **This is an assumption worth confirming** — see §9. |

### Nullability

Every column in all six contracts is currently declared `nullable: false`,
and every Raw column is therefore `NOT NULL`. This is a direct, literal
implementation of each contract's stated nullability — not an invented
constraint — per the Step 3.3.2 instruction to "implement contract-supported
nullability." If a future contract revision marks a column nullable, the
corresponding Raw column should be updated to match.

## 3. Metadata columns (DEC-004)

Every one of the six Raw tables gets exactly these four additive columns,
appended after the source columns:

| Column | Type | Purpose |
|---|---|---|
| `ingestion_timestamp` | `TIMESTAMPTZ` | When this row was ingested. Timezone-*aware*, unlike the source business timestamps above, because this value is generated by the pipeline itself (not parsed from ambiguous source text). |
| `source_file` | `TEXT` | Which physical source file this row came from. |
| `batch_id` | `TEXT` | Groups all rows loaded in the same ingestion batch. |
| `ingestion_run_id` | `TEXT` | Identifies the specific ingestion run/execution. |

These are ingestion metadata, not source columns, and are excluded from
`known_data_quality_findings` / contract validation.

## 4. No PK / FK constraints on the six Raw tables (DEC-002)

Confirmed: none of `raw.users`, `raw.products`, `raw.orders`,
`raw.order_items`, `raw.reviews`, `raw.events` declares a `PRIMARY KEY` or
`FOREIGN KEY` constraint at the database level. Rationale (carried forward
from DEC-002 and the Step 1 findings):

- Source data contains duplicate natural keys (e.g. `order_items` has 29
  rows sharing an `(order_id, product_id)` pair; `reviews` has 6 rows
  sharing `(order_id, product_id, user_id)`). A PK would make these rows
  unloadable.
- `order_items.user_id` and `reviews.user_id` are known-redundant
  (`orders.user_id` is the source of truth for ownership) — enforcing an FK
  on them here would encode a business assumption prematurely.
- Referential-integrity and uniqueness rules belong in Staging/Curated
  (dbt), once cleaning/business logic is applied.

No `CHECK` constraints are added either (e.g. no `accepted_values` /
regex-pattern / min-max enforcement) — those are explicitly deferred
business/data-quality rules per every contract's `deferred_business_rules`
section, not schema constraints.

## 5. `raw.ingestion_audit`

An operational log table, one row per (attempted) ingestion of one dataset
in one run — distinct from the six tables above in that it is **not** a
mirror of a source dataset.

| Column | Type | Notes |
|---|---|---|
| `audit_id` | `BIGSERIAL PRIMARY KEY` | Surrogate key. See §9 — this is the one place this step *does* add a PK, and why that's consistent with DEC-002 rather than a violation of it. |
| `ingestion_run_id` | `TEXT NOT NULL` | |
| `batch_id` | `TEXT NOT NULL` | |
| `dataset_name` | `TEXT NOT NULL` | e.g. `users`, `orders`, ... |
| `source_file` | `TEXT NOT NULL` | |
| `file_checksum` | `TEXT` | SHA-256 (DEC-003), nullable until computed. |
| `started_at` | `TIMESTAMPTZ NOT NULL` | |
| `completed_at` | `TIMESTAMPTZ` | Nullable — unset while a run is in flight or if it fails before completion. |
| `duration_seconds` | `NUMERIC(10,3)` | |
| `rows_read` | `INTEGER` | |
| `rows_loaded` | `INTEGER` | |
| `validation_status` | `TEXT` | e.g. `PASSED`, `FAILED`. |
| `load_status` | `TEXT` | e.g. `LOADED`, `SKIPPED_UNCHANGED` (DEC-003), `FAILED`. |
| `status` | `TEXT NOT NULL` | Overall run outcome. |
| `error_message` | `TEXT` | Nullable — populated only on failure. |

No CSV contents, passwords, credentials, or secrets are ever written to
this table.

## 6. Indexing

No indexes beyond the implicit one PostgreSQL creates for
`raw.ingestion_audit.audit_id` (its `PRIMARY KEY`). The six Raw tables have
no indexes: Raw is a full truncate/reload landing zone (DEC-001), not a
query-serving layer, so indexing is deferred to Staging/Curated where
access patterns are actually known.

## 7. Initialization mechanism

`database/init_db.py` is the **single** reproducible entry point:

```
python -m database.init_db
```

It executes `database/schema/raw_schema.sql` inside one transaction via the
connection utility in `database/connection.py`. The SQL script uses
`CREATE SCHEMA IF NOT EXISTS` / `CREATE TABLE IF NOT EXISTS` throughout, so
rerunning it against an already-initialized database is a no-op — safe to
call repeatedly (e.g. on every app/container startup) without a migration
framework. There is intentionally no second/competing initialization path.

## 8. Python database foundation

`database/connection.py` provides the minimum reusable pieces future
ingestion code will need, and nothing more:

- `DBConfig.from_env()` — reads `POSTGRES_HOST`, `POSTGRES_PORT` (default
  `5432`), `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` (see
  `.env.example`) and raises `DatabaseConfigError` if anything required is
  missing.
- `get_connection()` — opens a `psycopg2` connection (autocommit off).
- `transaction()` — a context manager: commits on clean exit, rolls back
  and re-raises on any exception, always closes the connection.
- `close_connection()` — safe connection close.

CSV loading, checksum computation, truncate/reload, and orchestration are
explicitly **not** implemented here — that is Step 3.3.3+.

## 9. Relationship to Data Contracts, and open decisions for approval

- Every table/column in this schema traces 1:1 back to a YAML contract in
  `ingestion/contracts/`. No columns, types, or constraints were invented
  beyond what a contract states or what DEC-004 requires (metadata columns).
- Two judgment calls were made where the brief didn't fully specify an
  answer, flagged here for confirmation rather than treated as settled:
  1. **Business timestamps stored as `TIMESTAMP` (no time zone)**, since
     the source ISO8601 strings carry no explicit UTC offset. If the
     source is actually known to be UTC, `TIMESTAMPTZ` may be preferable
     for `order_date` / `review_date` / `event_timestamp` later.
  2. **`raw.ingestion_audit` has a surrogate `BIGSERIAL PRIMARY KEY`**,
     even though the six dataset tables have none. This table isn't a
     mirror of source data — it's operational metadata this pipeline
     itself generates — so DEC-002's "preserve source fidelity" rationale
     doesn't apply to it. Flagging this interpretation for confirmation.

## 10. Relationship to future ingestion (Step 3.3.3+, not built here)

This step deliberately stops at structure. Not yet implemented (by design):
CSV readers, SHA-256 checksum comparison against `raw.ingestion_audit`
history (DEC-003), truncate+reload execution (DEC-001), retry/backoff
handling (DEC-007), or any orchestration (Airflow, dbt, Terraform). Those
tables and utilities are simply the foundation those future steps will
write into.
